## Q-01 · блокирует разработку · риск высокий (клиент)

**Кому:** архитектор

**Вопрос:** Каким HTTP-кодом метод отвечает, если сумма отклонена?

**Зачем:** Пример ERROR сейчас приведён под кодом 200. Приложение, которое смотрит на код, покажет «сохранено», хотя операция отклонена, а тестировщик не знает, какой код ждать для неверной суммы.

**Цена ошибки:** Клиент будет уверен, что порог сохранён, и не получит push, на который рассчитывал.

| Вариант ответа | Что это меняет |
| :--- | :--- |
| Кодом 400 с полем message, без поля result | Пример ERROR под 200 удаляется, поле result убирается или всегда равно OK, заголовок 200 исправляется. «Вернуть прежнее состояние» означает только то, что настройка не меняется. |
| Кодом 200 с result=ERROR и прежними amount и enabled | 400 остаётся только для неверного формата, а граница между 400 и ERROR задаётся списком случаев. Для первого сохранения определяется, какие amount и enabled вернуть. |

**Если ответа не будет, принимаем:** Отклонённая сумма получает 400 с message, код 200 означает только успешное сохранение.

**Закрывает находки:** D-005, D-025, D-026, D-030, D-060, D-065, D-067

**Ответ:** Кодом 400 с полем message, без поля result

## Q-02 · блокирует разработку · риск высокий (клиент)

**Кому:** владелец продукта

**Вопрос:** По какой дате покупка относится к месяцу учёта: по дате совершения или по дате проведения?

**Зачем:** Сейчас Ф-2 и критерий приёмки требуют разного. Пока ответа нет, расходы попадут не в тот месяц, push придёт клиенту не вовремя, а приёмка не пройдёт при любой реализации.

**Цена ошибки:** Если счётчик ошибается на границе месяца, клиент получает неверный push, а исправить уже накопленные суммы после выпуска трудно.

| Вариант ответа | Что это меняет |
| :--- | :--- |
| По дате совершения покупки, время UTC+5 | Ф-2 остаётся. Критерий приёмки №2 переписывается: сумма попадает в январский счётчик. Добавляется правило для push по событию, которое пришло после конца месяца. |
| По дате проведения покупки, время UTC+5 | Ф-2 переписывается, критерий №2 остаётся. Поздних событий за прошлый месяц не бывает. Цель «в момент покупки» переформулируется под проведение. |

**Если ответа не будет, принимаем:** Команда реализует Ф-2 как написано: дата совершения, время UTC+5. Критерий №2 будет исправлен, push по событию за закончившийся месяц отправляться не будет.

## Q-03 · блокирует разработку · риск высокий (безопасность)

**Кому:** архитектор

**Вопрос:** Остаётся ли сохранение порога запросом GET с параметрами в строке запроса?

**Зачем:** Браузер, прокси или повтор при сбое сети может незаметно для клиента повторить GET, ответ могут взять из кэша, а идентификатор карты попадает в журналы. Настройка клиента меняется непредсказуемо, а данные карты оказываются там, где их быть не должно.

**Цена ошибки:** Идентификатор карты в журналах прокси и веб-серверов — это утечка данных клиента, и найти её приходится уже после выпуска.

| Вариант ответа | Что это меняет |
| :--- | :--- |
| Нет, метод меняется на изменяющий состояние, параметры передаются в теле JSON | Правятся REST type и CURL, параметры переносятся из строки запроса в Request body, Content-Type становится оправданным, cardId уходит из строки запроса. |
| Да, GET остаётся | В документ добавляются обоснование, правила против кэширования и повторов, маскирование cardId в журналах и согласование с ИБ. |

**Если ответа не будет, принимаем:** Метод меняется на изменяющий состояние, параметры передаются в теле запроса.

## Q-04 · блокирует разработку · риск высокий (сроки)

**Кому:** архитектор

**Вопрос:** Какой сервис отдаёт приложению текущий порог, переключатель и сумму расходов за месяц?

**Зачем:** Экран показывает эти значения, но в части B есть только сохранение. Экран нельзя ни сделать, ни проверить, и сроки сорвутся на интеграции.

**Цена ошибки:** Без источника данных экран нельзя закончить, и выпуск задержится на время согласования нового API.

| Вариант ответа | Что это меняет |
| :--- | :--- |
| Новый метод чтения в части B возвращает все три значения | В часть B добавляется метод чтения. AlertsController берёт сумму у учёта расходов, архитектура и диаграмма последовательности дополняются этой связью. |
| Порог и переключатель отдаёт метод чтения в части B, сумму — отдельный метод сервиса расходов | В разделе интеграции описываются два метода из двух источников, перечень затронутых систем приводится к одному составу. |
| Сумма за месяц на экране не показывается | Из раздела UI убирается «сумма за месяц», в часть B добавляется только чтение настройки. |

**Если ответа не будет, принимаем:** Команда добавит метод чтения настройки в часть B, а сумму за месяц не будет показывать до ответа.

## Q-07 · блокирует разработку · риск высокий (деньги)

**Кому:** Архитектор интеграции

**Вопрос:** По какому полю распознаётся повторное событие и что делать с событием, пришедшим не по порядку?

**Зачем:** Система получает события от процессинга, которые на практике приходят повторно и не по порядку. В документе не названо поле, по которому определяется дубль, срок хранения этого ключа и поведение при событии, пришедшем раньше предыдущего. Без этого повтор события удвоит сумму или вызовет второе уведомление.

**Цена ошибки:** Не определён ключ идемпотентности и порядок обработки событий

| Ключ — идентификатор операции процессинга, дубль игнорируется | Нужно хранить идентификаторы операций весь период и описать это в требованиях к данным. |
| Ключ — идентификатор события доставки | Две доставки одной операции с разными идентификаторами события будут учтены дважды. |

**Если ответа не будет, принимаем:** Дубль определяется по идентификатору операции; события применяются по времени операции, а не по времени доставки.

## Q-08 · блокирует разработку · риск средний (клиент)

**Кому:** владелец продукта

**Вопрос:** Может ли карта получить второй push в том же календарном месяце?

**Зачем:** Ф-3 и Ф-4 дают разный результат, если порог сменили после push. Возврат и повторное включение уведомления тоже не описаны. Клиент рискует получить лишний push или не получить нужный, а модель хранения признака отправки нельзя спроектировать.

**Цена ошибки:** Лишние или пропущенные уведомления о бюджете вызовут жалобы клиентов, а разбирать их без однозначного правила нечем.

| Вариант ответа | Что это меняет |
| :--- | :--- |
| Нет, не больше одного push за месяц при любых изменениях | Ф-4 переписывается. Признак отправки хранится по карте за месяц, и его не сбрасывают ни смена порога, ни возврат, ни повторное включение. |
| Да, но только после смены порога | Признак отправки сбрасывается при сохранении нового порога, в Ф-3 добавляется исключение. Возврат и переключатель признак не сбрасывают. |
| Да, каждый раз, когда расходы опустились ниже действующего порога и снова его достигли | Признак сбрасывается при смене порога, после возврата и при повторном включении. Ограничение «один push в месяц» из Ф-3 удаляется, а учёт частичного возврата описывается явно. |

**Если ответа не будет, принимаем:** Действует Ф-3: один push на карту за месяц, что бы ни менялось.
