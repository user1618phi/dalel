### Цели
Клиент ограничивает сумму переводов по номеру телефона за календарные сутки, чтобы уменьшить потери при доступе посторонних лиц к Мобильному приложению.

### Архитектура решения
Мобильное приложение → Сервис лимитов: чтение и сохранение лимита. Сервис переводов → Сервис лимитов: запрос резервирования суммы перевода, события отмены и возврата. Сервис лимитов → Сервис push: запрос на отправку push.

### Дизайн процесса UI
Путь: Переводы → По номеру телефона → Лимит. Экран содержит поле «Дневной лимит, ₸», строку «Использовано сегодня, ₸» и кнопку «Сохранить». При ответе 400 под полем «Дневной лимит, ₸» показывается сообщение «Введите сумму от 1 000 до 2 000 000 ₸». Мобильное приложение показывает суммы в ₸ и передаёт их в REST API в тиынах. Тексты экрана на казахском и русском языках приведены в макете `https://design.example.test/phone-transfer-limit/v2`.

### Требования к изменениям

#### BPMN схема процесса
Подтверждение перевода клиентом → запрос резервирования суммы в Сервисе лимитов → при превышении лимита отказ до списания средств, в остальных случаях исполнение перевода → завершение. Схема: `https://design.example.test/phone-transfer-limit/bpmn-v2`.

#### Функциональные требования
* **Ф-1.** Клиент задаёт дневной лимит на переводы по номеру телефона от 1 000 ₸ до 2 000 000 ₸ включительно с шагом 1 ₸.
* **Ф-2.** Для клиента без сохранённой настройки дневной лимит равен 2 000 000 ₸.
* **Ф-3.** Календарные сутки перевода в часовом поясе UTC+5 (Asia/Almaty) определяются по времени подтверждения перевода клиентом, а не по времени зачисления получателю.
* **Ф-4.** В использованную сумму суток входит сумма каждого подтверждённого перевода по номеру телефона со всех счетов клиента.
* **Ф-5.** В использованную сумму суток не входят: переводы между своими счетами, переводы по номеру карты и платежи поставщикам услуг.
* **Ф-6.** Перевод со счёта в иностранной валюте входит в использованную сумму суток в сумме списания в KZT, которую Сервис переводов передаёт в запросе резервирования.
* **Ф-7.** Сервис лимитов отклоняет перевод с кодом `LIMIT_EXCEEDED` до списания средств, если использованная сумма суток вместе с суммой перевода превышает дневной лимит.
* **Ф-8.** Возврат перевода, в том числе частичный, уменьшает использованную сумму суток исходного перевода на сумму возврата.
* **Ф-9.** Отмена перевода уменьшает использованную сумму суток исходного перевода на полную сумму этого перевода.
* **Ф-10.** После каждого изменения значения лимита Сервис лимитов отправляет клиенту один push по шаблону из таблицы «Тексты push» на языке интерфейса Мобильного приложения.
* **Ф-11.** Push не содержит номера счёта, номера карты и номера телефона клиента.
* **Ф-12.** На экране блокировки устройства push показывается с тем же текстом, что и в центре уведомлений устройства.
* **Ф-13.** При ошибке доставки Сервис push повторяет отправку 3 раза с интервалом 60 с.
* **Ф-14.** После 3 неуспешных повторов сообщение сохраняется в разделе «Уведомления» Мобильного приложения.
* **Ф-15.** При сохранении лимита ниже использованной суммы суток новые переводы по номеру телефона отклоняются, пока использованная сумма суток не станет меньше лимита.
* **Ф-16.** При сохранении лимита, равного использованной сумме суток, новые переводы по номеру телефона отклоняются, пока использованная сумма суток не станет меньше лимита.
* **Ф-17.** При сохранении лимита выше использованной суммы суток следующий перевод исполняется, если его сумма не превышает разницу между новым лимитом и использованной суммой суток.

Таблица «Тексты push» (`{limit}` обозначает сохранённый дневной лимит в ₸ без дробной части):

| Язык | Шаблон текста push |
| :--- | :--- |
| Казахский | «Телефон нөмірі бойынша аударымдардың күндік лимиті өзгертілді: {limit} ₸.» |
| Русский | «Дневной лимит переводов по номеру телефона изменён: {limit} ₸.» |

### Sequence Diagram
Мобильное приложение → Сервис переводов: подтверждение перевода. Сервис переводов → Сервис лимитов: запрос резервирования суммы. Сервис лимитов → Сервис переводов: разрешение или отказ. Сервис лимитов → Сервис push: текст push и язык интерфейса после изменения лимита.

### Нефункциональные требования
* **НФ-1.** Сервис лимитов отвечает на запрос резервирования за время p95 ≤ 150 мс при нагрузке 300 запросов/с за 5-минутное окно измерения.
* **НФ-2.** Методы REST API отвечают за время p95 ≤ 300 мс при нагрузке 100 запросов/с за 5-минутное окно измерения.
* **НФ-3.** Доступность Сервиса лимитов составляет не менее 99,95 % за календарный месяц.
* **НФ-4.** Сервис лимитов выполняет проверку лимита и увеличение использованной суммы суток одной атомарной операцией на клиента.
* **НФ-5.** При недоступности Сервиса лимитов Сервис переводов отклоняет перевод по номеру телефона до списания средств.
* **НФ-6.** Сервис лимитов записывает в журнал аудита каждое изменение лимита с полями: идентификатор клиента, прежнее значение, новое значение, время изменения.
* **НФ-7.** Функционал включается для клиентов флагом `phone_transfer_limit_enabled` в Сервисе лимитов.
* **НФ-8.** Откат выполняется выключением флага `phone_transfer_limit_enabled` за время не более 5 минут без выпуска новой версии Мобильного приложения.

### Требования к данным
* **Д-1.** Сервис лимитов хранит по каждому переводу: идентификатор клиента, идентификатор перевода, идентификатор события, дату суток перевода, сумму перевода в тиынах.
* **Д-2.** Сервис лимитов хранит по каждому клиенту: дневной лимит в тиынах, использованную сумму текущих суток в тиынах.
* **Д-3.** Суммы в хранилище, в REST API и в событиях передаются целым числом в тиынах (1 ₸ = 100 тиын).
* **Д-4.** Записи о переводах удаляются через 13 месяцев после суток перевода.
* **Д-5.** Записи журнала аудита хранятся 5 лет с даты записи.

### Требования к интеграции
* **И-1.** Мобильное приложение читает и сохраняет лимит через методы дочернего документа «Лимит на переводы по номеру телефона — REST API».
* **И-2.** Сервис переводов передаёт в Сервис лимитов запрос резервирования `RESERVE` и события `CANCELLED`, `REFUNDED` с полями `eventId`, `transferId`, `clientId`, `amountTiyn`, `confirmedAt`.
* **И-3.** Событие `CANCELLED` или `REFUNDED`, полученное раньше запроса `RESERVE` того же перевода, ожидает его в очереди до 24 часов и применяется после его обработки.
* **И-4.** Событие, не дождавшееся `RESERVE` за 24 часа, переносится в очередь ошибок для разбора дежурным инженером.
* **И-5.** Ключом идемпотентности запроса `RESERVE` и событий служит поле `eventId`: сообщение с уже обработанным `eventId` не меняет использованную сумму суток и получает исходный ответ.
* **И-6.** Сервис лимитов публикует метрики мониторинга: время обработки события p95 и долю недоставленных push за 5-минутное окно; при превышении 5 с или 2 % дежурная смена получает оповещение.

## Часть B. REST API

Дочерний документ части A: «Лимит на переводы по номеру телефона — REST API». Документ описывает метод сохранения лимита (PUT) и метод чтения лимита (GET) одного ресурса.

### Общие параметры

| Поле | Значение |
| :--- | :--- |
| **Description** | Сохранение дневного лимита на переводы по номеру телефона |
| **REST type** | PUT |
| **Authorization** | Bearer, сессия клиента |
| **Controller** | PhoneTransferLimitController |
| **URL type** | Dev и Prod |
| **Request URL** | Dev: `https://api-dev.example.test/v1/clients/{clientId}/phone-transfer-limit`. Prod: `https://api.example.test/v1/clients/{clientId}/phone-transfer-limit` |
| **CURL** | `curl -X PUT "$BASE/v1/clients/$CLIENT_ID/phone-transfer-limit" -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" -d '{"limitTiyn":15000000}'` |
| **Swagger** | `https://api-dev.example.test/swagger/phone-transfer-limit` |
| **Gitlab project** | `https://gitlab.example.test/edu/phone-transfer-limit` |
| **Framework** | Spring Boot 3.3 |
| **Author** | Аналитик команды (учебная роль) |
| **Developer** | Команда разработки практикума (учебная роль) |

### Логика работы метода
1. Проверить пользовательскую сессию; при её отсутствии вернуть 401.
2. Проверить, что `clientId` совпадает с клиентом сессии; иначе вернуть 404.
3. Проверить, что клиенту подключены переводы по номеру телефона; иначе вернуть 403.
4. Проверить `limitTiyn` по разделу «Request body»; при нарушении вернуть 400 без изменения настройки.
5. Заменить настройку и вернуть 200 с сохранёнными значениями.
6. При внутренней ошибке вернуть 500 без изменения настройки.

### Особые правила
1. `limitTiyn` является целым числом в тиынах, кратным 100, от 100000 до 200000000, обе границы включены.
2. Повторное сохранение с тем же значением возвращает 200, не меняет настройку и не вызывает push.
3. Изменение лимита сохраняет использованную сумму суток.
4. Чтение лимита выполняется отдельным методом GET по тому же Request URL без тела запроса; метод GET не изменяет данные и возвращает те же поля ответа со статусами 200, 401, 403, 404, 500.
5. Для клиента без сохранённой настройки метод GET возвращает `limitTiyn` = 200000000.

| `clientId` | string | 1–64 | Да | Клиент сессии | Идентификатор клиента | `client_id` |

#### Query-параметры
Не используются.

#### Request body
* **Content-Type:** `application/json`.

| Parameter | Format | Size | Mandatory | Logic | Description | DB field |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| `limitTiyn` | integer | 64 bit | Да | От 100000 до 200000000, кратно 100 | Дневной лимит в тиынах | `limit_tiyn` |

### Ответ
Результат 200 является успешным. Результаты 400, 401, 403, 404 и 500 являются неуспешными и возвращают модель ошибки.

| Parameter | Format | Logic | Description | DB field |
| :--- | :--- | :--- | :--- | :--- |
| `limitTiyn` | integer | При успехе | Дневной лимит в тиынах | `limit_tiyn` |
| `usedTodayTiyn` | integer | При успехе | Использованная сумма текущих суток в тиынах | `used_today_tiyn` |
| `code` | string | При ошибке | Код ошибки: `VALIDATION_ERROR`, `UNAUTHORIZED`, `TRANSFERS_NOT_AVAILABLE`, `CLIENT_NOT_FOUND`, `INTERNAL_ERROR` | не хранится |
| `message` | string | При ошибке | Описание ошибки для журнала Мобильного приложения | не хранится |
| `traceId` | string | При ошибке | Идентификатор запроса для поиска в журнале | не хранится |

### Статусы

**200.** Ответ в случае успешного выполнения метода.  
**400.** Ответ в случае, если параметры запроса заполнены неверно.  
**401.** Ответ в случае, если запрос выполнен без необходимой авторизации.  
**403.** Ответ в случае, если `clientId` совпадает с клиентом сессии, но переводы по номеру телефона клиенту не подключены.  
**404.** Ответ в случае, если клиент `clientId` не найден или не совпадает с клиентом сессии.  
**500.** Ответ в случае, если произошла внутренняя ошибка сервера.

Все неуспешные ответы используют одну модель ошибки с полями `code`, `message`, `traceId`.

#### 200. Successful — OK
```json
{"limitTiyn":15000000,"usedTodayTiyn":6700000}
```

#### 400. Unsuccessful — Bad request
```json
{"code":"VALIDATION_ERROR","message":"Лимит вне диапазона от 100000 до 200000000","traceId":"f17a3c9e5b2d4086"}
```

#### 401. Unsuccessful — Unauthorized
```json
{"code":"UNAUTHORIZED","message":"Требуется вход","traceId":"0b6e8d4a2f9c4713"}
```

#### 403. Unsuccessful — Forbidden
```json
{"code":"TRANSFERS_NOT_AVAILABLE","message":"Переводы по номеру телефона не подключены","traceId":"1c9f5e7b3a8d4250"}
```

#### 404. Unsuccessful — Not found
```json
{"code":"CLIENT_NOT_FOUND","message":"Клиент не найден","traceId":"2d8a4f6c1b7e4399"}
```

#### 500. Unsuccessful — Internal server error
```json
{"code":"INTERNAL_ERROR","message":"Ошибка сервиса","traceId":"3e7b5a9d0c6f44a1"}
```
