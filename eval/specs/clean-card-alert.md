### Цели
Держатель карты получает push в момент, когда расходы по карте за календарный месяц достигают заданного им порога.

### Архитектура решения
Мобильное приложение → Сервис учёта расходов: чтение и сохранение настройки. Карточный процессинг → Сервис учёта расходов: события по покупкам. Сервис учёта расходов → Сервис push: запрос на отправку push.

### Дизайн процесса UI
Путь: Карты → Расходы → Уведомления. Экран содержит переключатель «Уведомлять о достижении порога», поле «Порог, ₸», строку «Расходы за месяц, ₸» и кнопку «Сохранить». При ответе 400 под полем «Порог, ₸» показывается сообщение «Введите сумму от 1 000 до 1 000 000 ₸». Мобильное приложение показывает суммы в ₸ и передаёт их в REST API в тиынах. Тексты экрана на казахском и русском языках приведены в макете `https://design.example.test/spend-alert/v3`.

### Требования к изменениям

#### BPMN схема процесса
Авторизация покупки → пересчёт расходов месяца → проверка порога → при переходе через порог отправка push → завершение. Схема: `https://design.example.test/spend-alert/bpmn-v3`.

#### Функциональные требования
* **Ф-1.** Держатель активной карты в KZT задаёт порог от 1 000 ₸ до 1 000 000 ₸ включительно с шагом 1 ₸.
* **Ф-2.** Для карты без сохранённой настройки уведомление выключено.
* **Ф-3.** Календарный месяц покупки в часовом поясе UTC+5 (Asia/Almaty) определяется по времени авторизации покупки, а не по времени её проведения.
* **Ф-4.** В расходы месяца входит сумма каждой авторизованной покупки по карте.
* **Ф-5.** В расходы месяца не входят: переводы, снятие наличных и комиссии банка.
* **Ф-6.** Покупка в иностранной валюте входит в расходы месяца в сумме списания со счёта карты в KZT, которую Карточный процессинг передаёт в событии.
* **Ф-7.** Возврат, в том числе частичный, уменьшает расходы месяца исходной покупки на сумму возврата.
* **Ф-8.** Отмена авторизации уменьшает расходы месяца исходной покупки на полную сумму этой покупки.
* **Ф-9.** Когда расходы месяца переходят от суммы ниже порога к сумме, равной порогу или выше, Сервис учёта расходов отправляет держателю карты один push по шаблону из таблицы «Тексты push» на языке интерфейса Мобильного приложения.
* **Ф-10.** После отправки push повторное достижение того же порога в том же календарном месяце не вызывает push.
* **Ф-11.** Из номера карты push содержит только последние 4 цифры.
* **Ф-12.** На экране блокировки устройства push показывается с тем же текстом, что и в центре уведомлений устройства.
* **Ф-13.** При ошибке доставки Сервис push повторяет отправку 3 раза с интервалом 60 с.
* **Ф-14.** После 3 неуспешных повторов сообщение сохраняется в разделе «Уведомления» Мобильного приложения.
* **Ф-15.** При сохранении настройки с порогом ниже накопленных расходов месяца push о достижении порога в текущем месяце не отправляется.
* **Ф-16.** При сохранении настройки с порогом, равным накопленным расходам месяца, push о достижении порога в текущем месяце не отправляется.
* **Ф-17.** При сохранении настройки с порогом выше накопленных расходов месяца следующее достижение порога вызывает push независимо от ранее отправленных push.

Таблица «Тексты push» (`{last4}` обозначает последние 4 цифры номера карты, `{threshold}` обозначает порог в ₸ без дробной части):

| Язык | Шаблон текста push |
| :--- | :--- |
| Казахский | «•{last4} картасы бойынша айлық шығыс {threshold} ₸ шегіне жетті.» |
| Русский | «Расходы по карте •{last4} за месяц достигли порога {threshold} ₸.» |

### Sequence Diagram
Карточный процессинг → Сервис учёта расходов: событие по покупке. Сервис учёта расходов → Сервис push: последние 4 цифры номера карты, порог и язык интерфейса при достижении порога. Сервис push → Мобильное приложение: push.

### Нефункциональные требования
* **НФ-1.** Сервис учёта расходов передаёт запрос на отправку push в Сервис push за время p95 ≤ 5 с от получения события при нагрузке 200 событий/с за 5-минутное окно измерения.
* **НФ-2.** Методы REST API отвечают за время p95 ≤ 300 мс при нагрузке 100 запросов/с за 5-минутное окно измерения.
* **НФ-3.** Доступность методов REST API составляет не менее 99,9 % за календарный месяц.
* **НФ-4.** Сервис учёта расходов записывает в журнал аудита каждое изменение настройки с полями: идентификатор клиента, идентификатор карты, прежнее значение, новое значение, время изменения.
* **НФ-5.** Функционал включается для клиентов флагом `spend_alert_enabled` в Сервисе учёта расходов.
* **НФ-6.** Откат выполняется выключением флага `spend_alert_enabled` за время не более 5 минут без выпуска новой версии Мобильного приложения.

### Требования к данным
* **Д-1.** Сервис учёта расходов хранит по каждой покупке: идентификатор карты, идентификатор операции, идентификатор события, месяц покупки, сумму покупки в тиынах.
* **Д-2.** Сервис учёта расходов хранит по каждой карте: порог в тиынах, признак включения, расходы месяца в тиынах, признак отправки push за месяц.
* **Д-3.** Суммы в хранилище, в REST API и в событиях передаются целым числом в тиынах (1 ₸ = 100 тиын).
* **Д-4.** Записи о покупках и расходы месяца удаляются через 13 месяцев после окончания месяца покупки.
* **Д-5.** Записи журнала аудита хранятся 5 лет с даты записи.

### Требования к интеграции
* **И-1.** Мобильное приложение читает и сохраняет настройку через методы дочернего документа «Уведомление о расходах по карте — REST API».
* **И-2.** Карточный процессинг передаёт в Сервис учёта расходов события `AUTHORIZED`, `REVERSED`, `REFUNDED` с полями `eventId`, `operationId`, `cardId`, `amountTiyn`, `authorizedAt`.
* **И-3.** Событие `REVERSED` или `REFUNDED`, полученное раньше события `AUTHORIZED` той же операции, ожидает его в очереди до 24 часов и применяется после его обработки.
* **И-4.** Событие, не дождавшееся `AUTHORIZED` за 24 часа, переносится в очередь ошибок для разбора дежурным инженером.
* **И-5.** Ключом идемпотентности события служит поле `eventId`: событие с уже обработанным `eventId` не меняет расходы месяца и не вызывает push.
* **И-6.** Сервис учёта расходов публикует метрики мониторинга: время обработки события p95 и долю недоставленных push за 5-минутное окно; при превышении 5 с или 2 % дежурная смена получает оповещение.

## Часть B. REST API

Дочерний документ части A: «Уведомление о расходах по карте — REST API». Документ описывает метод сохранения настройки (PUT) и метод чтения настройки (GET) одного ресурса.

### Общие параметры

| Поле | Значение |
| :--- | :--- |
| **Description** | Сохранение настройки порога расходов по карте |
| **REST type** | PUT |
| **Authorization** | Bearer, сессия владельца карты |
| **Controller** | SpendAlertController |
| **URL type** | Dev и Prod |
| **Request URL** | Dev: `https://api-dev.example.test/v1/cards/{cardId}/spend-alert`. Prod: `https://api.example.test/v1/cards/{cardId}/spend-alert` |
| **CURL** | `curl -X PUT "$BASE/v1/cards/$CARD_ID/spend-alert" -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" -d '{"thresholdTiyn":5000000,"enabled":true}'` |
| **Swagger** | `https://api-dev.example.test/swagger/spend-alert` |
| **Gitlab project** | `https://gitlab.example.test/edu/spend-alert` |
| **Framework** | Spring Boot 3.3 |
| **Author** | Аналитик команды (учебная роль) |
| **Developer** | Команда разработки практикума (учебная роль) |

### Логика работы метода
1. Проверить пользовательскую сессию; при её отсутствии вернуть 401.
2. Проверить, что карта `cardId` принадлежит клиенту сессии; иначе вернуть 404.
3. Проверить, что карта активна и ведётся в KZT; иначе вернуть 403.
4. Проверить `thresholdTiyn` и `enabled` по разделу «Request body»; при нарушении вернуть 400 без изменения настройки.
5. Заменить настройку и вернуть 200 с сохранёнными значениями.
6. При внутренней ошибке вернуть 500 без изменения настройки.

### Особые правила
1. `thresholdTiyn` является целым числом в тиынах, кратным 100, от 100000 до 100000000, обе границы включены.
2. Повторное сохранение с теми же значениями возвращает 200 и не меняет настройку.
3. Изменение порога сохраняет накопленные расходы месяца.
4. Чтение настройки выполняется отдельным методом GET по тому же Request URL без тела запроса; метод GET не изменяет данные и возвращает те же поля ответа со статусами 200, 401, 403, 404, 500.
5. Для карты без сохранённой настройки метод GET возвращает `enabled` = `false` и `thresholdTiyn` = 100000.

### Схема
```text
Мобильное приложение → SpendAlertController → Сервис учёта расходов → SpendAlertController → Мобильное приложение.
```

### Параметры запроса

#### Path-параметры
| Parameter | Format | Size | Mandatory | Logic | Description | DB field |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| `cardId` | string | 1–64 | Да | Карта клиента сессии | Идентификатор карты, не равный номеру карты | `card_id` |

#### Query-параметры
Не используются.

#### Request body
* **Content-Type:** `application/json`.

| Parameter | Format | Size | Mandatory | Logic | Description | DB field |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| `thresholdTiyn` | integer | 64 bit | Да | От 100000 до 100000000, кратно 100 | Порог в тиынах | `threshold_tiyn` |
| `enabled` | boolean | 1 bit | Да | `true` или `false` | Признак включения | `enabled` |

### Ответ
Результат 200 является успешным. Результаты 400, 401, 403, 404 и 500 являются неуспешными и возвращают модель ошибки.

| Parameter | Format | Logic | Description | DB field |
| :--- | :--- | :--- | :--- | :--- |
| `thresholdTiyn` | integer | При успехе | Порог в тиынах | `threshold_tiyn` |
| `enabled` | boolean | При успехе | Признак включения | `enabled` |
| `spentTiyn` | integer | При успехе | Расходы текущего месяца в тиынах | `spent_tiyn` |
| `code` | string | При ошибке | Код ошибки: `VALIDATION_ERROR`, `UNAUTHORIZED`, `CARD_NOT_ELIGIBLE`, `CARD_NOT_FOUND`, `INTERNAL_ERROR` | не хранится |
| `message` | string | При ошибке | Описание ошибки для журнала Мобильного приложения | не хранится |
| `traceId` | string | При ошибке | Идентификатор запроса для поиска в журнале | не хранится |

### Статусы

**200.** Ответ в случае успешного выполнения метода.  
**400.** Ответ в случае, если параметры запроса заполнены неверно.  
**401.** Ответ в случае, если запрос выполнен без необходимой авторизации.  
**403.** Ответ в случае, если карта принадлежит клиенту сессии, но не активна или ведётся не в KZT.  
**404.** Ответ в случае, если карта не найдена или принадлежит другому клиенту.  
**500.** Ответ в случае, если произошла внутренняя ошибка сервера.

Все неуспешные ответы используют одну модель ошибки с полями `code`, `message`, `traceId`.

#### 200. Successful — OK
```json
{"thresholdTiyn":5000000,"enabled":true,"spentTiyn":4850000}
```

#### 400. Unsuccessful — Bad request
```json
{"code":"VALIDATION_ERROR","message":"Порог вне диапазона от 100000 до 100000000","traceId":"a3f1c9d2e7b44f10"}
```

#### 401. Unsuccessful — Unauthorized
```json
{"code":"UNAUTHORIZED","message":"Требуется вход","traceId":"b84e02c61d5a4c27"}
```

#### 403. Unsuccessful — Forbidden
```json
{"code":"CARD_NOT_ELIGIBLE","message":"Карта не активна или ведётся не в KZT","traceId":"c5d7e1f09a3b4e68"}
```

#### 404. Unsuccessful — Not found
```json
{"code":"CARD_NOT_FOUND","message":"Карта не найдена","traceId":"d2a6b9c48f1e4d35"}
```

#### 500. Unsuccessful — Internal server error
```json
{"code":"INTERNAL_ERROR","message":"Ошибка сервиса","traceId":"e91f3a7b2c6d4a84"}
```
